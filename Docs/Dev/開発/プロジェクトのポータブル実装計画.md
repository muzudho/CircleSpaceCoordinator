記録日：2026-09-17。状態：未着手。今回実施したのはコード調査と計画の文書化のみ。

目的・利用シーン・仕様案は [プロジェクトのポータブル計画](../設計/プロジェクトのポータブル計画.md) を参照する。初版の到達点は「複数のフレーム配置案から選んで書き出し、受け取った側でも案を選んで取り込めること」。その後、定義・会場・配置内部・サークル情報などへ対象を広げる。

## 第０段階：選択・依存・形式の契約を確定

- [ ] 配置・型・定義・フレーム・セル・接続のID有効範囲と参照を棚卸しする。
- [ ] 初版の選択単位をフレーム配置案に固定し、必須同梱項目と省略項目を型ごとに記録する。
- [ ] 複数案で共有する型・ブロック表示と、案ごとに保持する定義の表現を決める。同じ定義IDでも案ごとの内容を勝手に統合しない。
- [ ] 新しい専用形式のDTOとスキーマを設計する。ファイル一覧と実データの対応、説明・タグ、必須マル秘、形式番号、件数・サイズ上限を決める。
- [ ] 未対応バージョン、未知の種類、壊れた参照、重複ID、空選択の扱いを決める。初版は未対応内容を黙って捨てず、理由を返す。
- [ ] フレーム配置２案、同じ型を共有する案、配置用定義が異なる案の架空サンプルを用意する。

完了条件：選択した案と必要な依存だけで成立するサンプルを示せる。旧形式の仕様を変更せず、新形式の仕様が文章とスキーマで一致している。

## 第１段階：初版の選択式受け渡し

### 1-A. エンジン側の抽出と読込み解析

- [ ] Application側に、スナップショットと選択IDから対象・依存を収集する処理を用意する。型名案は `PortableSelection` / `PortableDependencyResolver`。
- [ ] Infrastructure側に専用JSONの読書き・構造検証を用意し、既存のプロジェクト変換と意味検証を再利用する。
- [ ] 読込み解析を変更適用から分離する。内容一覧、依存理由、問題点を返し、開いているイベントや履歴を変更しない。
- [ ] 旧 `.frame-layout.json` を１項目の候補へ変換する互換アダプターを設ける。既存サービスを残し、必要な共通処理だけ段階的に移す。
- [ ] 新しい書出しはスナップショットから組み立て、定義の補完は出力側で行う案とする。元イベントへの変更が必要なら別の明示的編集として設計し、キャンセル・失敗で状態を変えない。
- [ ] Desktop.Coreはファイル操作・画面用状態、Desktop.Windowsは選択画面・OSダイアログを担当する。解析・抽出の照会APIはEngine.Model/Contracts、EditorEngine、EditorClient経由で接続する。

完了条件：GUIなしで、A・B・CからA・Cだけを書き出せる。サークル情報などの非対象データを含まず、旧形式も解析できる。

### 1-B. 取込み計画と一括適用

- [ ] 入力スナップショット・選択項目・取込先から、追加対象、依存、改名、衝突、ID対応を含む取込み計画を生成する。型名案は `PortableImportPlan`。
- [ ] 複数案同士と既存案の両方で、名前・ID・定義・ブロック表示の衝突を検査する。
- [ ] 会場の採用／保持／不一致を、確認画面と実適用で同じ規則から計算する。未選択項目だけの依存は取込対象から外す。
- [ ] `ImportPortableSelection` 相当の編集操作を追加し、候補プロジェクト全体を検証した後に１回だけコミットする。既存の `ImportFrameLayout` をUIから件数分実行する方式にはしない。
- [ ] 確認に使った入力データを固定し、取込先revisionを照合する。確認後にファイルやイベントが変わっても未確認の内容を適用しない。
- [ ] マル秘の継承、Undo/Redo、通常保存・再読込みを接続する。キャンセル・失敗時は状態と履歴を維持する。

完了条件：A・C入りファイルからCだけを追加できる。複数件もUndo/Redo各１回で往復でき、１件の失敗で一部だけ追加されない。

### 1-C. 選択画面と確認画面

- [ ] ［部分書出し］［部分読込み］の導線と、チェック可能な案一覧、全選択・解除、選択数を用意する。
- [ ] 名前・説明・タグの入力と表示、必須同梱項目・理由、マル秘表示を用意する。
- [ ] 読込み前に追加予定名、依存件数、会場の扱い、衝突理由を表示する。改名・見送り後に再計算する。
- [ ] 無選択、読込みエラー、未対応形式、会場不一致、マル秘警告、キャンセルの表示と操作を整える。
- [ ] 既存の配置１件の書出し・読込み導線を維持するか、新画面の１件選択へ統合するかを決め、既存利用者が迷わないラベル・案内を用意する。
- [ ] 通常のファイル上書き確認と、一時ファイルからの置換を接続する。長い名前・日本語IME・一覧スクロール・画面サイズを手動確認する。

完了条件：架空データで「送る側がA・Cを選び、受け取る側がCだけを採用する」操作をGUIで完走できる。

## 第２段階：定義・会場を素材として扱う

- [ ] 種類単位の選択と、定義単位の選択を追加する。
- [ ] 定義だけの保存先を設計する。特定の配置用定義への追加と共通カタログへの登録を区別する。
- [ ] 申込定義の参照先不足・同じ読込み値の異なる意味・定義の版の衝突を表示し、対応を選べるようにする。
- [ ] 会場単独の取込みについて、既存配置への影響と適用可否を確認できるようにする。
- [ ] 共通カタログへの保存を伴う場合、イベント内のUndoだけでは戻せない問題を解決し、適用・失敗・取消しの契約を別途定める。
- [ ] 説明・タグを利用するローカルのライブラリー一覧と検索を検討する。

完了条件：配置案を丸ごと含めなくても、定義や会場を保存・選択・再利用できる。参照先と保存先が明示され、既存データを暗黙に置換しない。

## 第３段階：細かな提案・差分採用へ広げる

- [ ] フレーム・島・領域の切り出し、座標の原点・挿入位置、境界をまたぐ接続や番号の扱いを設計する。
- [ ] サークルデータ・サークル配置の選択、参加者IDと配置先参照の解決、含まれる属性の確認を設計する。
- [ ] 重みチャンネル・評価設定の依存を調べ、参加者の列対応や会場座標の不一致を解決する。評価結果は取込み後に再計算する方針を検証する。
- [ ] 既存項目の更新・置換・差分採用を設計する。出所IDや同名だけで対象を決めず、影響する既存参照と変更内容を表示する。
- [ ] 会議向けの視覚プレビュー、ライブラリーのサムネイルや説明編集を追加する。

完了条件は各機能の着手時に具体化する。オンライン送信・公開・同時編集はこのファイル交換の実装とは分けて計画する。

## 初版の受入確認

| ケース | 期待結果 |
| --- | --- |
| ３案から２案を書出し、片方だけ取込み | 選択案と必須依存だけ追加される。既存案・サークル情報は保持 |
| 共通カタログのない環境で往復 | 配置時の定義、番号、旗・方向・接続・向かい合わせ領域を復元 |
| ２案の定義IDが同じで内容が異なる | 各案の定義を維持し、誤って共通化しない |
| 取込先と名前・型IDが衝突 | 改名や新規ID割当てにより参照を維持。無断上書きなし |
| 会場形状またはブロック表示が衝突 | 理由を表示し、イベントも履歴も変更しない |
| 未配置イベントへの取込み | 現行の判定に従って会場を採用し、確認表示と結果が一致 |
| 複数件のうち１件が不正 | 全件を適用せず、部分更新しない |
| 無選択・キャンセル・ファイル保存失敗 | 新たな変更なし。既存保存ファイルを壊さない |
| 確認後に取込先revisionが変化 | 古い計画を適用せず、再確認へ戻る |
| マル秘の書出し・部分取込み・再書出し | 警告・フラグを維持し、既存のマル秘も解除しない |
| 複数件のUndo/Redoと保存・再読込み | １操作として復元し、参照・定義・マル秘を維持 |
| 旧形式、新形式の不正version・参照・一覧不一致 | 旧形式は１候補として読める。不正な新形式は理由付きで拒否 |
| 元イベントに元表・パス・参加者・評価結果がある | 初版の出力JSONに混入しない |

検証は既存の実行可能テストに追加する。抽出・一括適用はApplication.Tests、JSONはInfrastructure.Tests、gRPCとrevision・履歴はEngine.Tests、ファイル操作と画面用状態はDesktop.Testsを中心にする。必要に応じてCore.TestsやStationeryUI.Testsを追加し、実行方法は [テスト手順](../../../tests/README.md) に従う。
