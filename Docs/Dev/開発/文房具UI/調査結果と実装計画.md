# 調査結果と実装計画

この文書は調査時点の対応表と計画です。現在の完了・残作業・検証状況は [移行進捗](移行進捗.md) を参照してください。

方針更新：ファイル選択ダイアログは Windows 側に残すことが確定した。以下の「ファイル選択を新設」「一画面化」は当初案であり、ファイル選択には適用しない。IME の OS 接続も Windows 側へ分離する。[下線入力と共通化方針](下線入力と共通化方針.md) を参照。

## 目的と調査範囲

2026-09-06、CircleSpaceCoordinator と、別リポジトリーの `KifuwarabeGo2026.StationeryUI` のローカルソースを照合した。目的は、別ウィンドウとして開く Windows フォームを減らし、会議参加者が共有対象のウィンドウだけで操作を追えるようにすること。

参照元は `KifuwarabeGo2026/KifuwarabeGo2026.StationeryUI`。主要な調査対象は `Presentation/StationeryUI/Controls/Button/Button.cs`、`Controls/SinglelineTextUnderline/TextInputDialog.cs`、`Controls/TextUnderlineController.cs`、`MessageDialog/MessageDialog.cs`、`SpinButton/SpinButton.cs`、`Platform/`、`Presentation/KfwScreenCanvas.cs`。文字入力の接続例は同リポジトリーの `KifuwarabeGo2026.GameOasis.Gui/Game1.cs` にある。

文房具 UI は MonoGame の画面内に描く方式で、この目的に適している。ただし、そのまま全 Windows フォームを置き換えられる完成品ではない。

Discord は複数のウィンドウキャプチャ方式を使用するため、別ダイアログが必ず映らないとは断定しない。同じ描画画面内へ統一することで共有対象から外れる問題を減らせると判断した。実際の共有結果は受信側で検証する必要がある。[Discord 公式のキャプチャ方式説明](https://support.discord.com/hc/en-us/articles/9410427556375--Windows-Capturing-Application-Window-for-Screen-Share-and-Go-Live)

## 統合時の注意

1. 現在の `ShowDialog()` 待ちをそのまま置き換えない。表示中も `Update` / `Draw` を続け、確定・取消の結果を受けて編集処理を実行する。入力中は背後の配置操作とショートカットを遮断し、閉じたクリックが背後へ流れないようにする。
2. 日本語入力は描画だけで完成しない。`Window.TextInput`、IME の未確定文字列、選択・キャレット、クリップボードを接続する。囲碁側と会場側の `ITextCompositionService` は形が異なる。囲碁側の Windows 実装は `GameOasis.Gui.Windows/Infrastructure/Windows/` にある。OS の変換候補一覧の共有可否は別途確認する。
3. 囲碁側のダイアログは 1920×1080 の仮想画面を前提とする。可変ウィンドウに対して描画とヒット判定を同じ変換に揃える。`KfwScreenCanvas` を使う場合は `Fonts/Ui` の SpriteFont 資産も必要。描画コールバックで既存描画へ接続する方法もある。
4. 囲碁側は `net8.0` と MonoGame `3.8.*`、会場側は .NET 10 と MonoGame `3.8.5.1`。移植時は依存バージョンを明示的に揃える。別リポジトリーへの絶対パス参照を公開プロジェクトへ追加しない。
5. 汎用部品は `CircleSpaceCoordinator.StationeryUI`、会場固有の操作は `Desktop.Core`、OS 実装は `Desktop.Windows` に分ける。今回のボタンは既存の座標型と描画コールバックを使い、StationeryUI の MonoGame 非依存を維持する。
6. 移植元・変更内容・ライセンスを記録する。囲碁側の名前空間やフォントなどを暗黙の依存として残さない。
