## 今回の実装

- `StationeryUI/Controls/ModalDialogModel.cs`：通知・確認・分数指定・進捗の状態と操作結果。OS・MonoGame には依存しない。
- `Desktop.Windows/VenueEditorGame.Dialogs.cs`：同じ MonoGame 画面への描画、文房具ボタン、入力処理、最適化処理との接続。既存の文字描画を利用する。
- `VenueEditorGame.cs`：描画の最後へモーダルを重ね、表示中は通常の編集入力より先に処理する。削除・最適化の入口を非同期の結果処理へ変更。
- `OptimizationSettingsDialog.cs` と `OptimizationProgressDialog.cs`：使用を終えた旧 Windows フォーム実装を削除。

文房具 UI の画面内描画・ボタンを利用する構成だが、囲碁側の固定解像度ダイアログ全体をそのままコピーしたものではない。会場アプリの可変ウィンドウと、既存の MonoGame 非依存の UI モデルへ合わせている。

## 入力と処理の仕様

モーダル表示中は、背後のドラッグ・ショートカット・配置操作を遮断する。開く操作と閉じる操作で使ったキー・左ボタンが離されるまでは、次の操作へ進めない。これにより、閉じた直後の Escape でアプリが終了したり、クリックが背後へ通ったりすることを防ぐ。

ボタンは押してから同じボタン内で離した場合に実行する。Tab で次のボタンへ移動し、Enter／Space で実行する。削除確認の初期選択はキャンセル。時間指定は −／＋ または矢印キーで 1 分ずつ変更する。Escape は通常のダイアログでは取消／閉じる、進捗画面ではストップ要求になる。

最適化は `Task.Run` で実行し、進捗は最新値だけをスレッド間で受け渡す。結果の配置案追加はゲームの Update 側で行う。ストップを要求しても画面は閉じず、最高案の確定完了を待つ。ゲーム破棄時にも停止要求を出し、完了後にリソースを解放する。画面の非アクティブ中も計算は継続し、画面へ戻ったときに結果を処理する。

表示はウィンドウ内に収まるパネルを使い、サイズ変更時にボタンを配置し直す。長い本文は各行を縮小表示する方式で、本文スクロールや自動折返しはまだない。

## 検証と手動確認

Release ビルドで警告・エラー 0 件を確認。C# テスト 134 件（Application 44、Core 24、Desktop 44、Infrastructure 12、StationeryUI 10）と配布チェック 7 件が成功した。追加テストは、確認の取消後に確定できないこと、時間の上限・下限、ストップが一度だけ通知され完了までモーダルを閉じないことを検証する。文書内のローカルリンクも確認済み。

次の手動確認は架空サンプルで実施する。

1. 机配置の削除を開いて Escape／キャンセルを選び、配置が残り、アプリも終了しないこと。
2. 削除確認中に背後の机・配置案・Ctrl+S 等が反応しないこと。
3. 最適化の時間を変更し、キャンセルすると計算を始めないこと。
4. 最適化を開始し、画面が更新され続けること。ストップ後、改善した場合だけ新しい配置案が追加されること。
5. 表示中のリサイズ、別アプリへの切替と復帰、ボタン外でのマウス解放を確認すること。
6. Discord でアプリのウィンドウを共有し、受信側で確認・時間指定・進捗・結果が見えること。

## 次の担当者へ

下線入力を既存配置の名前変更へ試験導入した。まず IME の確定／未確定、キャレット、選択、貼付け、文字数制限、Enter が変換確定とダイアログ確定の両方に流れないことを実機で確認する。その後、作成・複製や `DeskNumberDialog` へ展開する。実装の境界と制限は [下線入力と共通化方針](下線入力と共通化方針.md) に記載。

ファイル選択は利用者の指定により Windows 側に残す。ファイルシステムの操作自体は共通化可能だが、ファイル選択 UI は OS の機能を利用する。IME の接続も Windows 側に置き、編集状態を持つ文房具 UI とは分離する。

残っている `ShowDialog` / `MessageBox.Show` は `CircleSpaceCoordinator.Desktop.Windows` のソースを検索して追跡できる。新しい入口は「表示を開いた」ときに戻り、結果はコールバックで処理するため、旧来の同期的な戻り値をそのまま使わない。
