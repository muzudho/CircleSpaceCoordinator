# 下線入力と共通化方針

## 決まった方針

ファイル選択ダイアログは Windows 側に残す。ファイルシステムの読込み・保存処理そのものは OS 共通の .NET API を使えるが、選択 UI は OS の機能に任せる。ファイル選択中は別ウィンドウとなり、画面共有で同じように映ることは保証しない。

IME とクリップボードも OS 接続を Windows 側へ置く。文房具 UI は入力された文字と編集状態を扱い、WinForms の TextBox を所有しない。

## 下線入力の試験導入

2026-09-06、既存の机配置・サークル配置の「Rename」と、旧形式の配置案名変更に導入した。配置の新規作成・複製、イベント名、机番号、席名などはまだ旧ダイアログを使用する。

枠で囲むテキストボックスの代わりに、名前の下へ緑色の線を引く。入力にフォーカスがあると線を太くし、キャレットと選択範囲を表示する。入力中は空白文字を入力でき、確定ボタンの操作と区別する。確定時は前後の空白を除去し、空白だけの名前を拒否する。

| 配置先 | 責務 |
| --- | --- |
| `StationeryUI/Text/UnderlineTextEditor.cs` | 単一行、選択、カーソル移動、挿入・削除、Undo/Redo、文字数制限 |
| `StationeryUI/Text/ITextInputService.cs` | 確定文字・変換中文字列、入力範囲、クリップボードを渡す OS 境界 |
| `Desktop.Windows/Text/WindowsTextInputService.cs` | DesktopGL の SDL 文字入力イベントと Windows クリップボードの実装 |
| `Desktop.Windows/VenueEditorGame.TextInput.cs` | 文房具式の下線・選択・キャレット描画、キー操作、名前変更との接続 |

SDL のイベント監視は囲碁側の WindowsTextCompositionService の方式を参考にしている。Win32 の WndProc 差替えは行わず、現在の SDL ウィンドウ ID の文字入力・変換中文字列をキュー経由でゲーム側へ渡す。確定文字を Window.TextInput と二重に取り込まない。入力が閉じたらイベント監視を解除する。

これは囲碁側の UI ライブラリー全体の導入ではなく、下線表現を会場アプリの既存の共通座標・文房具ボタンに合わせた試験実装。以前の `ITextCompositionService` は既存の境界として残っており、新しい入力画面は確定文字も扱う `ITextInputService` を使う。独立化の前にこの API の整理も行う。

## 操作と制限

- 開くと名前を全選択。入力で置換し、左右・Home/End で移動、Shift 併用で選択する。
- 入力欄のクリックでキャレット移動。Ctrl+A/C/V/X、Ctrl+Z/Y を利用できる。
- Tab で入力欄・キャンセル・確定を循環する。Enter で確定、Escape で取消。IME の更新や確定文字が届いたフレームと、その後の Enter/Escape の解放までは、ダイアログの確定・取消を抑制する。
- 上限は従来同様に UTF-16 の 100 単位。カーソル移動・削除・切り詰めでは文字要素の境界を使い、絵文字のサロゲートペアや結合文字を途中で切らない。
- 長い名前は縮小表示。横スクロール、マウスドラッグ選択、キー長押しの自動反復はまだない。
- 変換中文字列には黄色の下線を表示する。IME 内のキャレット位置や文節選択の完全な再現、変換候補一覧の自前描画は未対応。候補一覧は OS に任せる。
- 現在は SDL の通常の TEXTEDITING / TEXTINPUT イベントを扱う。拡張編集イベントや長い未確定文字列を含む IME の実機確認は残っている。

## 確認状況

Release ビルドは警告・エラー 0 件で成功。文字選択と Undo/Redo、絵文字・結合文字の削除、単一行・文字数上限の自動テストを追加した。これらは OS 非依存の編集状態のテストであり、IME の実動作を保証しない。

Windows IME と Discord の実機確認は未実施。架空サンプルの既存配置を Rename し、日本語変換の Enter で画面が閉じないこと、次の Enter で名前が変わること、Escape で元の名前が残ることを確認する。選択置換・貼付け・空白の入力・リサイズ・アプリ切替も確認してから、他の入力画面へ展開する。

## 独立リポジトリー化について

独立化には賛成。２つのアプリでボタンや文字入力を使うようになったため、共通部品の修正を１か所で管理する利点がある。ただし、今すぐ片方のフォルダーをそのまま切り出すより、両アプリで使える境界を確認してから切り出す方がよい。

候補は次の構成。プロジェクト名はまだ案であり、リポジトリー作成やパッケージ公開は行っていない。

| パッケージ候補 | 責務 |
| --- | --- |
| `StationeryUI.Core` | 編集・選択・フォーカス・入力サービスの抽象。OS と描画エンジンを参照しない |
| `StationeryUI.MonoGame` | 文房具の下線・付箋・ボタン・ダイアログ描画と入力接続 |
| `StationeryUI.Windows` | 共用できる Windows IME・クリップボードの実装。必要になった段階で切り出す |

会場の配置モデル、囲碁のルール、画面固有の文言・操作、アプリの設定保存は各アプリ側に残す。Windows のファイル選択も当面は各アプリ側に置く。

順序は、下線入力を実機で評価 → ２アプリで使う最小 API と描画資産を整理 → 囲碁固有の名前空間を除去 → ライセンス・テスト・サンプルを含めて独立 → 各アプリが固定バージョンのパッケージを参照、を提案する。MonoGame のバージョンとフォントの供給方法を明示し、別リポジトリーへの絶対パス参照や可変バージョンに依存しない。
