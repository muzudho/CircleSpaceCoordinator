# Circle Space Coordinator 開発引き継ぎ

## 1. プロジェクトの目的

イベント会場をグリッドとして扱い、机と参加者を配置した複数の案を評価・比較するツールを開発する。

既存版はExcelを方眼紙として使用している。参加者の属性値と座席位置ごとの重みを掛け合わせ、候補となる `XPlan0` ～ `XPlan8` などの配置案から、会場評価値が最も高い案を選ぶ。

新しい実装では、MonoGame上で机をドラッグ＆ドロップできる会場エディターを作る。Excelは画面や評価エンジンとしてではなく、既存入力の取込みと提出物の生成に使う。

## 2. 既存Python版

既存実装は `CircleSpaceCoordinator/` にある。

- `main.py`: 全体の処理順を制御する。
- `scripts/ready.py`: Excelブック、シート、名前付き範囲、検索処理を初期化する。
- `scripts/format_x_*.py`: 配置案に参加者属性を展開する。
- `scripts/format_w_*.py`: 座席位置別の重みシートを整形する。
- `scripts/predict_*.py`: 属性値と位置別重みを掛け、項目別評価値を計算する。
- `scripts/models/plan_book_model.py`: 配置案ブックと重みブックを開閉する。

概略の評価式は次のとおり。

```text
項目別評価値 = Σ（参加者属性値 × 配置セルの重み）× Scale + Offset
```

確認できた評価項目は次の5種類。

- 有償頒布物数
- 紙の書籍の有無
- 持ち込み予定機材数
- デスクトップディスプレイ数
- 本部関係者かどうか

Python側には、5項目を合算して最良案を決定する処理は見当たらない。総合評価と案の選択は、現在のExcel数式または人間による確認が担当している可能性が高い。

## 3. ローカルExcelブック

業務用ブックは次の場所にあるが、個人情報や業務情報を含む可能性があるためGitへ追加しない。

```text
CircleSpaceCoordinator/deployment-v5.xlsm
```

値を表示せず構造だけ確認した結果は次のとおり。

- シート: `README`, `Result`, `YPredict`, `Config`, `Data`, `SpaceConfig`
- 名前付き範囲: `VenueArea`
- `Data` シートは匿名化のため実データがほぼ取り除かれている。
- ルートおよびPythonプロジェクト内の `.gitignore` で `.xlsm` を除外している。

既存コードはほかに次のローカルブックを利用する。

- `deployment-v5-XPlan{番号}.xlsx`: 候補配置案
- `deployment-v5-weight.xlsx`: 座席位置別の重み

公開用テストでは、架空の参加者だけを含む最小ブックを新しく作ること。

## 4. 採用したアーキテクチャー

アプリ本体と評価計算はC#で統一する。Pythonはopenpyxlを使うExcel入出力アダプターとして残す。

```text
MonoGame Desktop
       |
Application
       |
Core domain and evaluator
       |
versioned JSON / CSV
       |
Python openpyxl bridge
       |
.xlsm input / submitted workbook
```

PythonとC#の両方へ評価式を持たせ続けない。移行完了後はC#の計算結果をPythonがExcelへ書き込む。

CSVは参加者一覧などの表形式データに利用できる。会場、机、重みマップ、複数の配置案を含むプロジェクト全体の正規保存形式には、`schemaVersion` を持つJSONを使う。

詳細は [architecture.md](../architecture.md) を参照すること。

### Core

会場、座標、セル、机、参加者、配置案、重みマップ、制約、評価結果を置く。MonoGame、Excel、JSONへ依存させない。

### Application

配置案の作成・複製・比較、机の移動と回転、参加者の割当て、再評価、Undo対象の編集操作を置く。

### Infrastructure

JSON、CSV、設定、ログなどを置く。Excel固有処理は置かない。

version 1 JSONとCoreモデルを相互変換する `ProjectJsonSerializer` は実装済み。匿名サンプルの読込み、評価、評価結果付きJSONへの書戻し、再読込みまでテスト済み。

### StationeryUI

MonoGame用のUIライブラリー。別リポジトリー `KifuwarabeGo2026` にある自作UIから、囲碁固有の名前空間と依存を外して移植する予定。

移植元の主な資産:

- `TextBoxController`: キャレット、選択、クリップボード、Undo/Redo、キーリピート
- `SinglelineTextUnderline`: 通常・ホバー・編集中の表示
- `TextInputDialog`: 選択、キャレット、IME未確定文字列の描画
- `ITextCompositionService`: OS固有IME処理の抽象
- `WindowsTextCompositionService`: Win32およびSDLのIME composition取得

Windows固有実装は `StationeryUI` へ混ぜず、`Desktop` 側から抽象サービスとして注入する。

### Desktop

MonoGameアプリの起動、会場キャンバス、カメラ、机のドラッグ＆ドロップ、ヒートマップ、評価比較画面を置く。

### Excel bridge

既存 `.xlsm` の取込み、名前付き範囲とセル座標の変換、VBAを保持した保存、提出用Excel生成を担当する。

2026-09-01時点でimport側の初版は実装済み。

- `VenueArea` を0始まり会場グリッドへ変換
- `a/b` を横並び2セル机へ変換
- `ab` とその右隣空セルを2スペース用の2セル机へ復元
- `Data` を参加者と5つのfeatureへ変換
- `XPlan` のサークルID入力セルを `ScoringPosition` に変換
- 2スペース参加者へ同じ机の2セルを割当て
- 任意のData列から `CombinedSpaceId` を取込み
- 重みブックと `YPredict` のScale/Offsetを取込み
- Data欠落時だけ明示オプションで匿名プレースホルダーを生成
- dry-runと既存出力の上書き防止

匿名化されたローカルブックで、37×22会場、124参加者、1配置案、124割当てを一時JSONへ変換し、C#で読込み・意味検証・評価まで成功している。一時JSONは検証後に削除済み。

## 7. 次の実装順

### Step 1: 交換データ契約を決める

最初にJSONの最小スキーマを決める。少なくとも次を表現する。

- `schemaVersion`
- 会場の幅と高さ
- 使用可能セル、壁、通路、入口など
- 机のID、占有セル数、位置、向き
- 参加者IDと属性値
- 配置案と机・参加者の割当て
- 評価項目と位置別重み
- Scale、Offset、総合点への係数

業務上の実列名をそのまま公開契約へ持ち込む前に、公開可能か確認する。

### Step 2: Coreの最小モデルを作る

推奨する最初の型:

- `GridPosition`
- `Venue`
- `Desk`
- `DeskOrientation`
- `Participant`
- `ParticipantFeatures`
- `Placement`
- `Plan`
- `WeightMap`
- `EvaluationBreakdown`
- `EvaluationResult`

最初は1セル机と2セル机、整数座標だけを扱う。

2026-09-01時点で初期実装は完了している。実装済み:

- `GridPosition` と90度単位の回転
- `Venue`、`DeskType`、`DeskPlacement`
- `Participant`、`ParticipantAssignment`、`Plan`
- 評価項目、重みマップ、項目別結果、総合結果
- プロジェクト全体の意味検証
- 既存Python互換の位置別加重和、Scale、Offset
- 総合比較用のOverallWeight

参加者は物理的な机ではなくスペースセルへ割り当てる。2スペース参加者は2セルを占有するが、旧ExcelでサークルIDが入っている主セル `ScoringPosition` だけを評価計算に使う。

「合体スペース」は2サークルが同じ物理机を合同利用する配置。同じ `CombinedSpaceId` を持つちょうど2参加者が、一つの `DeskPlacement` の占有セル内へ収まる必要がある。隣接していても別々の机に分かれていれば配置違反。

### Step 3: 評価式を移植する

Pythonと同じ入力を与えたとき、項目別評価値が一致するテストを先に作る。浮動小数点の許容誤差も明示する。

Core単体の評価テストは作成済み。次は匿名化したExcel由来のfixtureを用意し、既存Pythonとの一致テストへ進む。

### Step 4: Excel importを作る

`tools/excel-bridge` に、既存ブックから匿名化JSONへ変換するコマンドを作る。実データを誤って出力・コミットしないよう、出力先は `data/private/` または `data/exchange/` とし、どちらもGit対象外にしてある。

初版は実装済み。利用方法は `tools/excel-bridge/README.md` を参照すること。次は実データを表示せずに列対応と合体スペース列名を実運用ブックで確認し、fixtureを増やす。

### Step 5: MonoGameとStationeryUIを追加する

CoreがGUIなしでテストできる状態になってから、会場グリッドと机のドラッグ操作を実装する。IME対応テキスト入力は移植元から必要部分だけを持ってくる。

### Step 6: Excel exportを作る

C#が出力した評価結果と選択案を、Pythonが提出用ブックへ書き戻す。openpyxlは数式を再計算しないため、提出手順でExcelによる再計算が必要か検証する。

## 8. 既存Pythonの注意点

- モジュールのimport時にブックを開く処理がある。
- 検索関数は最初の空セルで探索を終了する。
- 一部の評価処理は入力値が `int` の場合だけ加点する。
- `except:` が広く、ファイル破損や権限エラーを「ファイルなし」と誤認する可能性がある。
- `predict_*.py` と `format_*.py` に重複コードが多い。
- openpyxlはExcel数式を計算しない。

既存版を整理する場合も、まず評価値の一致テストを作り、提出作業を壊さないこと。

## 9. 作業上の注意

- 作業ツリーには、ユーザーが編集中の個人用文書が存在する。無関係な差分を変更、整形、削除しない。
- `.xlsm` や実データをコマンド出力へ表示しない。
- シート構造だけを調べる場合も、値のダンプは避ける。
- 既存Pythonファイルは移行テストが整うまで現在位置に残す。
- 新規依存を追加するときは、MonoGameの対象プラットフォームと.NETバージョンを先に確認する。

## 10. 完成の目安

- MonoGame上で1セル机・2セル机を配置、移動、回転できる。
- 参加者を机へ割り当てられる。
- 複数案を保存、複製、比較できる。
- 項目別ヒートマップと評価内訳を表示できる。
- C#の評価値が既存Python版と一致する。
- `.xlsm` またはCSVから入力できる。
- 提出用Excelを生成できる。
- 実データなしで自動テストを実行できる。
