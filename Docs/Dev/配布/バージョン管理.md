# リリース用バージョン番号

`Directory.Build.props` の `Version` を、Desktop・Project CLI・自作 DLL に共通するリリース番号の正本とします。初期値は `1.0.0` です。バージョンを設定しただけでは GitHub Release やタグは作成されません。

## 番号の付け方

`メジャー.マイナー.パッチ` の3つの整数で管理します。

- パッチ：不具合修正。例：`1.0.0` → `1.0.1`。
- マイナー：互換性を維持した機能追加。例：`1.0.1` → `1.1.0`。
- メジャー：利用方法やデータの互換性に影響する大きな変更。例：`1.1.0` → `2.0.0`。

同じ番号で異なる配布内容を公開し直さず、会議中の修正・再配布でも新しい番号を付けます。この構成では正式な3桁の番号を使います。プレリリース表記を導入する場合は AssemblyVersion・FileVersion と ZIP の検証処理も対応させてください。

イベント JSON や設定の `schemaVersion` はデータ形式の番号です。アプリのリリース番号とは別に管理し、リリースのたびに変更しません。外部ライブラリーのバージョンも変更しません。

## 番号を確認する

- Desktop：イベント選択画面と編集画面のタイトルに `Circle Space Coordinator v1.0.0` のように表示します。
- CLI：`CircleSpaceCoordinator.ProjectCli.exe --version` で表示します。
- EXE・自作 DLL：ファイルのプロパティで製品バージョン・ファイルバージョンを確認できます。
- ローカル配布 ZIP：`CircleSpaceCoordinator.Desktop-v1.0.0-win-x64-日時.zip` の形式になります。

`AssemblyVersion` と `FileVersion` は `Version` に `.0` を付けた4桁です。SDK が製品バージョンへ付けるコミット識別情報（`+...`）は、画面表示・CLI の出力・ZIP 名では省略します。Git 管理情報を含まないソース ZIP からのビルドでも、リリース番号そのものは変わりません。

## リリース前の作業

1. リポジトリーのルートにある `Directory.Build.props` の `<Version>` を更新します。画面や CLI に番号を直接書き込む必要はありません。
2. 変更内容を記録し、[テスト手順](../../../tests/README.md) を実行します。
3. Release ビルド後、タイトル・CLI・ファイルの番号を確認します。
4. バージョン更新を含めたソースをコミットし、公開するコミットを確定します。
5. ソースの版を固定して配布する場合は、そのコミットに `v1.0.0` のようなタグを付け、タグと同じ番号で GitHub Release を作成します。一度公開したタグは別の内容へ付け替えません。

ソース配布では、利用者に対象タグを案内してください。GitHub の Code → Download ZIP を使う場合も、先にそのタグを選ぶことで対象版を取得できます。既定ブランチのソースには、リリース後の開発変更が含まれる場合があります。

ローカル署名 ZIP の作成方法は [リリース手順](リリース手順.md) を参照してください。有料署名や CI の導入は、バージョン管理の前提ではありません。
