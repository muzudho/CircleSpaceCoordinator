# コード署名

このリポジトリの Desktop アプリと ProjectCli の Release publish 出力にある EXE/DLL を署名する手順です。

現在の方針と関連資料は [配布に関する知見](README.md) を参照してください。自己署名の検証結果が `Valid` でも、Smart App Control（SAC）の許可は保証しません。

## 開発用の自己署名証明書

次のコマンドを PowerShell で実行します。証明書は現在のユーザーの証明書ストアにだけ作成・信頼登録され、秘密鍵はリポジトリに保存されません。

```powershell
$certificate = .\scripts\ForSmartAppControl\New-DevelopmentCodeSigningCertificate.ps1
$certificate.Thumbprint
```

出力された拇印を指定して、Release publish と署名を実行します。

```powershell
.\scripts\ForSmartAppControl\Publish-AndSign.ps1 -CertificateThumbprint '<拇印>'
```

成果物は `artifacts/signed` に作成されます。特定の Windows ランタイム向けに publish する場合は `-RuntimeIdentifier win-x64` を追加します。

Desktop アプリは MonoGame が `SDL2.dll` などのネイティブ DLL を動的に読み込むため、単一 EXE にはまとめません。署名・検証するのは `Sign-ReleaseArtifacts.ps1` の許可リストにある、このリポジトリで作成する EXE/DLL だけです。MonoGame、SDL2、StationeryUI などの外部ライブラリは提供元のファイルを維持し、自己署名の追加や署名の上書きを行いません。JSON、画像など実行コードではないファイルにも Authenticode 署名を付けません。配布時は EXE だけを取り出さず、生成されたフォルダー全体を ZIP にしてください。

自己署名証明書は作成した Windows ユーザーでのみ信頼されます。他の PC に配布する用途や Smart App Control の信頼を得る用途には使用しません。

## 公開リリース用の CA/EV 証明書

以下は Windows の証明書ストアから秘密鍵を利用できる環境向けの既存手順です。現在の公開用コード署名証明書はハードウェアでの秘密鍵保管が必要で、PFX をインポートするだけで利用できるとは限りません。USB トークン・クラウド署名では発行元の設定と署名ツールに合わせた対応が必要です。[SSL.com の保管要件](https://www.ssl.com/products/software-integrity/code-signing/)

既存スクリプトと互換性がある場合は、その証明書の拇印とタイムスタンプサーバーを指定します。このリポジトリーでは購入した証明書による動作検証は未実施です。

```powershell
.\scripts\ForSmartAppControl\Publish-AndSign.ps1 `
  -CertificateThumbprint '<CA または EV 証明書の拇印>' `
  -RuntimeIdentifier win-x64 `
  -TimestampServer 'http://timestamp.digicert.com'
```

PFX のパスワードや秘密鍵をリポジトリ、ソースコード、ログに保存しないでください。EV 証明書の USB トークンまたはクラウド署名を使う場合は、認証局の署名ツールで publish 出力の EXE/DLL を署名してください。

## 署名のみを行う場合

既存の publish 出力は次のように再帰的に署名・検証できます。

```powershell
.\scripts\ForSmartAppControl\Sign-ReleaseArtifacts.ps1 `
  -Path '.\artifacts\signed\CircleSpaceCoordinator.Desktop.Windows' `
  -CertificateThumbprint '<拇印>' `
  -TimestampServer 'http://timestamp.digicert.com'
```

## Visual Studio の F5 実行

`CircleSpaceCoordinator.Desktop.Windows` の Debug ビルドでは、ビルド完了後に
`scripts/ForSmartAppControl/Sign-BuildOutput.ps1` が自動実行されます。
現在の Windows ユーザーの証明書ストアから有効な開発用証明書を選び、
`bin/Debug` の EXE/DLL を署名してからアプリを起動します。

一時的に自動署名を無効化する場合は、MSBuild プロパティ
`SmartAppControlSigningEnabled=false` を指定してください。

## 配布方式の検討記録

### 2026-09-09: F5 起動失敗と既存の開発用署名の照合

通常ユーザー環境で Desktop.Windows の Debug ビルドと自動署名は成功しましたが、起動時に `CircleSpaceCoordinator.EditorClient.dll` の読み込みが `0x800711C7` で拒否されました。Code Integrity イベント 3033 / 3077 のポリシー ID は `{0283ac0f-fff1-49ae-ada1-8a933130cad6}` でした。

拒否された DLL の Authenticode は `Valid` で、署名者・発行者はいずれも `CN=CircleSpaceCoordinator Development Code Signing` です。同じ証明書が通常ユーザーの `My`、`Root`、`TrustedPublisher` に登録済みであることも確認しました。同梱エンジンの EXE / DLL の署名検証にも `Valid` 以外はありませんでした。したがって、今回確認した範囲では証明書の未作成・信頼登録漏れ・エンジンの署名漏れが原因ではありません。

参考として `D:\github.com\muzudho\KifuwarabeGo2026` の Docs、PowerShell スクリプト、ビルド設定を調査しました。現在のローカルファイルには自己署名の自動化処理は見つかりませんでした。同リポジトリの `Docs/Dev/トラブルシューティング/Smart App Controlによる再生成DLLブロック調査.md`（2026-08-29）にも、自己署名のローカル信頼だけでは SAC の許可を保証できない旨が記載されています。別のチェックアウトやリポジトリ外の手順については未確認です。

[Microsoft の SAC 署名ガイド](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/code-signing-for-smart-app-control)でも、SAC が考慮するのは信頼されたプロバイダー発行の証明書とされています。ローカルの署名検証成功と SAC の起動許可は分けて確認します。既存の証明書と自動署名は維持し、この調査では新しい証明書の作成、OS ポリシーの変更、有料サービスの導入は行っていません。F5 起動失敗は未解決です。

なお、Codex の隔離環境では通常ユーザーの証明書ストアが見えず「証明書がない」というビルドエラーになりました。通常ユーザー側での確認結果と混同しないでください。自動署名の必要性は [Smart App Control による起動ブロック](../Troubleshooting/Smart%20App%20Controlによる起動ブロック.md) の手順で切り分けます。
