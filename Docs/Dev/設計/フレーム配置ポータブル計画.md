# フレーム配置ポータブル計画

記録日：2026-09-16。調査基準：v1.8.0。初版実装：2026-09-17。

後続構想（2026-09-17）：選択式の部分保存・受渡しへの拡張は [プロジェクトのポータブル計画](プロジェクトのポータブル計画.md)、作業手順は [実装計画](../開発/プロジェクトのポータブル実装計画.md) を参照。後続構想は未実装で、以下の初版の実装とは区別する。

## 初版の実装と操作

- イベントリストで対象を選び、［編集］から会場名を入力・保存する。既存の `Venue.Name` を使い、書出しのたびに入力する必要はない。
- ［フレーム配置］ページの［配置データ書出し］から、選択中の配置１件を `.frame-layout.json` に書き出す。保存済みの会場名を表示し、マル秘チェックもここで付けられる。
- 同じ［フレーム配置］ページの［配置データ読込］から、現在のイベントへフレーム配置案を追加する。プロジェクトJSONの保存先は尋ねず、イベント名・既存の配置案・サークルデータを保持する。読込みは１回の［元に戻す］で取り消せる。変更をファイルに残すときは通常のイベント保存を使う。
- 読込み確認には［読込］と［名前を付けて読込］を表示する。現在のイベント内に同名のフレーム配置案があるときは［名前を付けて読込］と［キャンセル］にし、配置案の重複しない名前を求める。入力名は追加する配置案だけに使う。マル秘の書出し確認も専用の［書き出す］ラベルを使う。
- 読み込んだフレーム配置案のサークル配置案は、［サークル配置］の［＋］で作る。既存のサークルデータを使うか、［サークルデータ］ページから別途読み込む。
- 会場はイベント内で共通なので、既存の配置がある場合は寸法・障害物・ゾーンの一致を確認し、相違があれば理由を表示して追加を拒否する。未配置のイベントでは読込データの会場を採用する。同番号のブロック表示設定が異なる場合も上書きせず拒否する。フレームの型IDは新しく割り当て、既存の型との衝突を避ける。
- フレーム定義と申込スペース定義は `DeskLayout.Definitions` にまとめる。定義編集または書出しを行った時点で、この配置用の定義になる。編集後はイベントを保存する。共通カタログには書き戻さない。まだ配置用定義がない旧イベントは共通カタログをひな形として使う。
- 書出し対象は使用中の型と申込定義の参照先。申込定義は配置用カタログの全件を含める。旧イベントの当時の対応は復元できないので、必要に応じて書出し前にカタログで調整する。
- 配置済みフレームとカタログで同じ定義IDの形状が異なる場合は、理由を表示して書出しを止める。初版では版を選ぶ専用画面はなく、定義を配置時の内容へ揃えるか、現在の定義で配置し直して解決する。
- イベントまたは配置がマル秘なら書出し前に警告。読込み前にも警告し、追加する配置と現在のイベントにフラグを継承する。既存のマル秘は解除しない。確認をキャンセルするとファイルも開いているイベントも変更しない。再書出しでもフラグは残る。
- 重みチャンネル・評価結果・サークル情報・元表・書出し先・表示位置・アプリ設定は含めない。会場、障害物、ゾーン、フレーム位置と回転、番号、ブロック表示、旗・方向・補助接続・接続解除・向かい合わせ領域は含める。

形式は `kind: circle-space-frame-layout`、`formatVersion: 1`、必須の `isConfidential`、サークル情報を除いたイベント構造の `project` からなる。既存イベントのシリアライズ・検証をエンジン経由で再利用する。定義モデルはCoreへ移動し、旧イベントは追加フィールドなしでも読める。

実装入口：`CircleSpaceCoordinator.Desktop.Core/Persistence/FrameLayoutPortableService.cs`、`CircleSpaceCoordinator.Desktop.Windows/VenueEditorGame.Portable.cs`。スキーマは `schemas/frame-layout-v1.schema.json`。以下は初版前の調査・設計記録で、未採用の後続案を含む。

## 目的と利用の流れ

フレーム配置の担当者とサークル配置の担当者が異なる運用に対応する。フレーム配置の担当者から、［サークルデータ］と［フレーム配置図］を別々に渡せるようにする。受け取った人は、自分のPCの共通カタログに同じ定義がなくても配置図を開き、サークルデータを読み込んでサークル配置案を作成できる。

ここでいう［フレーム配置図］は画像ではなく、位置や定義を復元して編集を続けられるデータを指す。画像出力とは別の機能として扱う。

## 利用者からの要件

- フレーム配置図のエクスポートとインポートを用意する。
- フレーム定義、申込スペース定義、フレーム配置、島定義を一緒に渡す。
- 会場情報は既存の `Venue.Name` を［会場名］として活用する。例：`２０２６年夏ぴよぴよ会館東棟２階`。
- 申込スペース定義をフレーム配置図側で管理できるようにする。
- ［マル秘］フラグを持たせ、エクスポート・インポート時に警告する。

以下の具体的な形式・所有範囲・取込規則は、これらを実現するための推奨案。既存機能として説明しないこと。

## 現在のデータ構造

| 対象 | 現在の保存場所・型 | 注意点 |
| --- | --- | --- |
| 共通フレーム定義 | EXEの隣の `space-definitions.json` の `SpaceDefinitionCatalog.Types` | 名前、種類、寸法、セル状態、外周の辺、内部接続を保存。イベントとは別ファイル |
| 共通申込スペース定義 | 同ファイルの `SpaceDefinitionCatalog.Requests` | 読込み値、説明、フレームへの参照。イベントJSONには含まれない |
| 配置に使用したフレームの型 | イベントの `DeskTypes` / `DeskType.Space` | 配置時点の定義をコピー。型IDには定義内容のハッシュを含むため、共通カタログの後日の変更で配置済みの形は変わらない |
| フレーム配置 | イベントの `DeskLayouts` / `DeskLayout` | フレームごとの型ID、位置、回転、フレーム番号を保持 |
| 番地 | `DeskPlacement.DeskNumber` と `DeskLayout.SeatLabels` | フレーム番号、ブロック番号、セル番号。見た目だけでなく書出しにも必要 |
| 島定義 | `DeskLayout` の各プロパティ | 旗・入口方向、接続補助線、自動接続の解除、向かい合わせ領域 |
| 会場 | イベントの `Venue` | ID、会場名（`Name`）、幅、高さ、障害物、ゾーン |
| 表示設定 | イベントの `BlockStyles` など | 番号に対応する色・網掛けを含む |
| マル秘 | イベントの `CircleSpaceProject.IsConfidential` | 既存イベントに警告表示用フラグがある。配置図単体のフラグはまだない |
| サークル配置案 | イベントの `CircleLayouts` | `DeskLayoutId` でフレーム配置を参照。割当と手動の仮置きを持つ |

現在のJSON保存は `DeskLayouts` と `CircleLayouts` を分けて行う。`Plan` は旧形式の互換読込みや、両者を合わせて編集・評価する際にも使われるため、ポータブル形式を旧 `Plans` の丸ごとコピーで作らない。

## 推奨する受渡し単位

初版は**選択したフレーム配置１件を、依存する定義と会場情報を含む１ファイルとして渡す**。複数配置の一括書出しは後続とする。

| 含めるもの | 範囲 |
| --- | --- |
| 識別・形式情報 | ファイル種別、形式バージョン、受渡しデータのID、名前、任意の説明 |
| マル秘 | 配置図の `IsConfidential` |
| 会場 | 会場名（`Venue.Name`）、寸法、障害物、ゾーン |
| フレーム配置 | 選択した配置のフレームと位置・回転・番号 |
| フレーム定義 | 配置で使用する型と、同梱する申込スペース定義が参照する型 |
| 申込スペース定義 | 対象のフレーム配置に属する定義一式 |
| 島定義 | 対象配置の旗・入口方向・接続・接続解除・向かい合わせ領域 |
| 番地と見た目 | ブロック番号・セル番号、必要なブロックの色・網掛け |

サークル一覧・元の入力表・サークル配置案・割当・仮置き・書出し先パス・操作ログ・アプリ設定・ピン留めは含めない。サークルデータは別に受け渡す。自動整列した未配置の石は表示用の位置なので、このファイルに保存しない。

重みチャンネルや評価設定には、会場側のセル情報と参加者の入力列への対応がある。実装前に保存先と参照を追い、会場側の情報を落とさず、参加者情報やローカルファイルパスを混入させない依存範囲を確定する。イベントの `Evaluation` 全体を無条件で同梱する設計にはしない。

形式は専用の種別識別子を持つJSONを推奨する。拡張子の案は `.frame-layout.json`、種別は `circle-space-frame-layout`。初版のファイル形式番号をイベントJSONの形式番号とは別に管理する。これらの名称は実装時に確定する。

## 既存の会場名を活用

既存の `Venue.Name` を会場名の保存先として使い、イベントJSONとポータブル形式の両方で引き継ぐ。利用者との合意により、場所専用の `Location` プロパティや別の入力欄は追加しない。

- UIのラベルは［会場名］。１行の自由入力とし、住所形式や地名の検索は要求しない。
- 年、棟、階、ホールなどをそのまま書ける。全角文字を勝手に半角へ変換しない。
- 旧ファイルの `Venue.Name` はそのまま読み込み、別フィールドへの移行や自動改名を行わない。
- エクスポート前とインポート前の確認画面に表示する。
- 空欄の扱いと文字数上限は既存の会場名の検証規則に揃える。ポータブル機能だけで別の規則を導入しない。

現在は１イベントに１つの `Venue` がある。この制約のまま、異なる会場名・寸法の配置を同じイベントへ無条件で取り込まない。

## 申込スペース定義を配置図側へまとめる

**共通カタログは作成時のひな形、フレーム配置図内の定義は受渡しと編集に使う正本**とする案を推奨する。異なるPCの共通カタログに依存しないことが重要。

### 所有範囲

`DeskLayout` に対応する配置図用カタログをイベント内へ追加する。実装案は `DeskLayout` ごとの `Definitions` とし、フレーム定義・申込スペース定義をまとめる。現行のDesktop.Coreの永続化型をCoreから参照せず、共通モデルをCore側へ分離して、既存共通カタログ用の変換を残す。

同じイベント内でも、フレーム配置ごとに申込スペースの対応付けを保持できる。サークル配置担当者が対象フレーム配置を選んだときは、その配置図側の定義を使用する。申込スペース定義の対応付けだけで割当・最適化にどの制約まで強制されるかは、既存処理を調べて明示し、受渡し機能の追加だけで未実装の割当制約が有効になったと説明しない。

### 配置済みの型との整合

配置済みフレームの実体はイベントの `DeskTypes` を基準にする。共通カタログに同じ `DefinitionId` があっても、現在の内容が配置当時と同じとは限らない。配置図用の参照は、実際の型の版を識別できるIDへ変換する。区画番号を再導入しない。

申込定義だけが参照する未配置のフレーム型も同梱する。同じひな形から作った複数の版が存在して対応先を一意に決められない場合は、候補を表示して解決してから書き出す。

### 既存イベントからの移行

1. 配置済みフレームの型をイベントから集める。
2. 既存の共通申込スペース定義から、対象配置で使う定義を取り込む候補を提示する。
3. 読込み値、参照先、型の版、重複・不足を確認し、配置図用の定義として保存する。
4. 移行後は共通カタログの変更で配置図用定義を自動更新しない。

過去のイベントには申込スペース定義のスナップショットがないため、当時の対応付けを完全には自動復元できない。共通カタログがないPCでは必要な定義を入力してもらい、名前や番号だけから対応を推測して確定しない。意図的に申込定義を使わない配置図には空の一覧を認め、不足を解決していない状態とは区別する。

## インポート時の衝突と会場の扱い

初版の推奨導線は［フレーム配置図から新しいイベントを作成］。既存のサークルデータに取り込みたい運用もあるため、［現在のイベントに新しいフレーム配置として追加］を用意する場合は、次の規則を満たすこと。

- 同名の配置や定義があっても上書きしない。新しい配置IDを発行する。
- 受渡しファイル内のIDから取込先IDへの対応表を作り、型・フレーム・番号・旗・接続・申込先を一括で張り替える。
- 同じIDで異なる内容の型は別IDとする。内容の同一性を確認せず既存型を再利用しない。
- 共通カタログは変更しない。共通ひな形への登録は将来の明示的な別操作とする。
- 同じ申込読込み値の意味が異なる場合も、配置図ごとの定義として区別する。イベント共通の１件へ暗黙に統合しない。
- 会場情報が異なる既存イベントへの追加は中止し、差分と新しいイベントとして開く導線を表示する。会場名だけが異なる場合を許容するかは追加設計事項とする。
- 既存のサークル配置案の参照先を勝手に変更しない。新しい配置図に対してサークル配置案を作る。

構文・形式番号・必須項目・参照・セル座標・重複・辺設定・接続を検証してから変更する。未対応形式や壊れた参照は理由を表示して中止する。読込み失敗・警告のキャンセルで、イベントや共通カタログを部分更新しない。

## マル秘フラグと警告

ポータブルファイルとイベント内のフレーム配置図に `IsConfidential` を持たせる。現在のイベント単位のフラグも維持する。マル秘は警告と表示のための情報であり、暗号化やアクセス制御ではない。

### エクスポート

書出しファイルのフラグは、イベントと対象配置図のフラグの論理和とする。マル秘イベントから取り出した配置図を、暗黙に通常扱いにしない。

マル秘なら、ファイルを作成する前にアプリ内の警告を表示する。

> このフレーム配置図は［マル秘］です。会場名・配置・定義がファイルに含まれます。渡す相手と保存先を確認してください。

表示項目は、配置図名、会場名、マル秘表示、同梱範囲、保存先。ボタンは［キャンセル］と［警告を確認して書き出す］とし、初期の操作対象はキャンセルにする。通常のファイル保存先・既存ファイル上書きの確認は別に扱う。確定までは受渡しファイルを作成しない。

### インポート

ファイルを読み取って構造を検証した後、イベントへ適用する前にマル秘警告を表示する。

> このフレーム配置図には［マル秘］が付いています。取り込んだ後もマル秘として扱います。取り込み先を確認してください。

表示項目は配置図名、会場名、取込先、マル秘を引き継ぐこと。ボタンは［キャンセル］と［警告を確認して取り込む］とし、初期の操作対象はキャンセルにする。

取込先イベントのフラグは `既存イベントのフラグ OR 読み込んだフラグ`。通常の配置図を取り込んでも、既存イベントのマル秘を解除しない。警告を了承したことをマル秘解除の意味にしない。取り込んだ配置図を再エクスポートしてもフラグを保持する。初版ではマル秘を解除する操作を追加しない。

一般の取込前画面にもマル秘の有無を表示する。新形式ではフラグを必須項目として検証し、欠落・型不正を黙って `false` にしない。既存イベントJSONにフラグがない場合の互換読込みとは区別する。

既存イベントへの取込みは１操作としてUndo/Redoできる設計にする。Undoでは取込前の状態へ戻し、取込前から付いていたマル秘を消さない。Redoで再び取り込む際もマル秘を復元する。

## 実装を進める順序

1. 既存の会場名の利用と配置図用定義のモデル、所有範囲、IDの参照規則を固める。旧イベントの移行方法と会場差分の扱いを確認する。
2. Coreの型、イベントJSON・スキーマ、ヘッドレスエンジンの操作契約へ追加する。旧ファイルの読込みを維持する。
3. InfrastructureにポータブルJSONの読書きと検証、Applicationに依存収集・移行・取込の一括操作を実装する。
4. 既存の会場名を編集できる導線と配置図側の定義編集を整え、共通カタログとの違いを画面上で示す。
5. フレーム配置ページへエクスポート・インポート導線、プレビュー、マル秘警告を追加する。
6. 新しいPC相当の空カタログで往復検証し、サークルデータを別読込みして配置作業を続けられることを確認する。

画面の選択状態は緑背景、操作対象は水色枠にする。既存の下部ツールヒントを利用し、警告はアプリ画面内に表示する。ファイル選択は既存のOSダイアログの方式に揃える。

## 受入確認

- 共通カタログのない環境で、受け取った１ファイルから会場・会場名・フレーム・申込定義・島・番号を復元できる。
- 回転したフレーム、配置未確定セル、壁・入口・１つの正面、非隣接接続、接続解除、旗の入口方向を往復で保持する。
- 別途サークルデータを読み込んで配置案を作成でき、石を配置できる。
- 型の同名・同ID異内容・複数版、未配置型への申込参照、重複した読込み値を正しく扱う。
- 受取側の共通カタログ、既存配置、サークル配置案、手動の仮置き、書出し対象を無断で変更しない。
- 会場名の全角文字を往復で保持し、既存の検証規則と旧イベントの読込みを維持する。
- マル秘の入出力・再出力で毎回必要な警告が出て、キャンセルでは変更もファイル作成も起こらない。
- 既存／取込フラグの４通り、Undo/Redo、形式不正・フラグ欠落を検証する。
- 別の会場への誤取込みを拒否し、新規イベントとして開ける。
- サークル個人データ・元表・ローカルパス・設定・ログが受渡しファイルに混ざらない。
