# プロジェクトのポータブル計画

記録日：2026-09-17。状態：構想・設計案。今回の作業は文書化までで、以下の拡張機能は未実装。

実装手順は [プロジェクトのポータブル実装計画](../開発/プロジェクトのポータブル実装計画.md)。既存機能の記録は [フレーム配置ポータブル計画](フレーム配置ポータブル計画.md) の冒頭「初版の実装と操作」を参照する。

## 目的と利用者の要望

プロジェクトの一部を選んで保存・受け渡しし、受け取った側も必要な部分だけを選んで取り込めるようにする。フレーム配置の受け渡しを発展させ、知見のライブラリー化とオンラインミーティングでの提案・採用に使う。

利用者から示された要望は次のとおり。

- 現在のプロジェクトから、何をエクスポートするかピックアップしたい。
- エクスポートされたデータから、何をインポートするかピックアップしたい。
- プロジェクトの部分的保存・部分的受け渡しを可能にしたい。
- 知見を蓄積して再利用し、オンラインミーティングのコミュニケーション方法へ発展させたい。
- 「プロジェクトのポータブル計画」という名前で構想と実装計画を引き継げるようにしたい。
- サークルデータを含めないことを重要な条件とする。
- フレーム配置の重みチャンネルと、それに対応するサークル側の列の意味・入力ルールを、運営の知見として保存・配布したい。
- 知見自体を必要に応じてマル秘にし、イベント運営が内部で持つ知見を内部共有するツールへ発展させたい。

以下の選択単位、形式名、段階分け、衝突規則は推奨案であり、利用者が細部まで確定した仕様ではない。

## 想定する使い方

1. 担当者が配置案A・B・CからAとCを選び、「通路を広めにした案」などの説明を添えてファイルにする。
2. 会議中にファイルを受け取った人が内容を確認し、Cだけを現在のイベントへ追加する。
3. 後日、蓄積したファイルを開き、用途や工夫を読んで別のイベントへ再利用する。
4. 将来は定義だけ、会場だけ、配置の一部なども素材として取り出せるようにする。

通常のプロジェクト保存は作業全体の保存として維持する。ポータブルファイルは選択した内容のスナップショットであり、元プロジェクトの削除・移動や双方向同期を伴わない。部分保存したファイルだけで元プロジェクト全体を復元できるとは説明しない。オンライン会議でのファイル受け渡しをまず支え、チャット送信・クラウド公開・リアルタイム共同編集は別の将来課題とする。

## 2026-09-17時点の実装

- `.frame-layout.json` は `kind: circle-space-frame-layout`、`formatVersion: 1`。フレーム配置１件と会場・定義などを含む専用JSON。
- 書出しは選択中の配置１件。読込みはファイル内の配置一式を現在のイベントへ新しい案として追加する。ファイルの中から一部を選ぶ画面はない。
- `DeskLayout.Definitions` が配置用の定義を保持し、未設定の旧イベントでは共通カタログをひな形にする。
- サークル情報、元表、重みチャンネル、評価結果、表示位置、書出し先などは含めない。
- 配置済みのイベントでは会場の寸法・障害物・ゾーンの相違を拒否する。会場名はこの形状比較には含まれず、既存会場を保持する。未配置判定を満たす場合は入力側の会場を採用する。
- 同名配置は改名を求め、型IDは新規割当てする。同番号のブロック表示設定が異なる場合は拒否する。
- 取込みは１回のUndoで戻せる。マル秘の警告と継承がある。

旧計画の本文には実装前の案も残っている。現行コードと冒頭の実装記録を優先して読むこと。

## 選択する単位と関連データ

「利用者が選ぶもの」と「それを成立させるために必要なもの」を画面で区別する。依存するデータを黙って追加せず、同梱理由と件数を示す。必須の依存を外す場合は、依存元の選択も外すか、後続段階で検証済みの既存データへの対応付けを求める。

| 対象 | 推奨する開始段階 | 関連データ・注意点 |
| --- | --- | --- |
| フレーム配置案 | 初版。複数案から個別選択 | 会場、使用型、配置用定義、番号、島定義、必要なブロック表示を含む |
| フレーム定義・申込スペース定義 | 第２段階。定義単位 | 申込定義の参照先も必要。配置用定義と共通カタログの所有先を区別する |
| 会場 | 第２段階。会場一式 | イベント全体で共通。既存配置への影響を確認する |
| 配置内のフレーム・島・領域 | 第３段階 | 境界をまたぐ接続、旗、番地、座標の原点と挿入位置の規則が必要 |
| 重みチャンネル・入力ルール | 第１段階の後の優先拡張（第1.5段階） | チャンネル単位で選択。席の重み、狙い、対応列の意味・入力ルールを含む。サークル実データは不要 |
| その他の評価設定 | 第３段階 | 選択チャンネルの係数は第1.5段階で扱い、それ以外の設定は依存を調査。計算結果は含めない |
| サークルデータ・サークル配置案 | 本計画の対象外 | 参加者一覧・属性値・元表・割当・仮置きを含めない。列の仕様だけを知見として扱う |

初版は「複数のフレーム配置案から、書出す側も読込む側も案を選ぶ」ところまでを通して実現する。これだけで計画全体を完了とはしない。種類単位・配置内部の選択へ段階的に広げる。

初版の配置用申込定義は、現行と同じく各配置の全件を含め、参照するフレーム定義も含める。未使用の申込定義を勝手に削除しない。定義単位の選択は第２段階で扱う。

## 重みチャンネルを運営の知見として共有する（2026-09-17追記）

利用者が共有したいのは、席の評価値だけでなく「なぜその値にするか」「対応する列に何を入力するか」を含む運営上の判断ルールである。サークルデータなしでも保存・閲覧・受け渡しできることを要件とする。

### 利用者が示した具体例

| 項目 | ［書籍の有無］チャンネルの知見 |
| --- | --- |
| 席側の重み | 明るい席は `1.000`、照明が暗い席は `-1.000` |
| 対応するサークル側の列 | ［書籍の有無］ |
| 列の入力ルール | 書籍があれば `1`、無ければ空欄（数値としては `0`） |
| 狙いの説明例 | 書籍のあるサークルを明るい席へ配置する判断に使う |

重みと属性値を掛ける部分では、書籍ありなら明るい席で `+1`、暗い席で `-1`、書籍なしならどちらも `0` になる。他チャンネルや補正係数を含む最終評価・配置を保証するものではない。空欄を0と解釈することと、必要な列そのものが存在しないことは区別する。

### 保存する内容の推奨案

- チャンネルの名前、説明、用途、判断の理由、適用条件。
- 列の仕様：推奨列名、意味、数値型、値ごとの意味、空欄の扱い。この例では `1`＝書籍あり、`0`／空欄＝書籍なし。実際のサークルごとの入力値は含めない。
- 席の重み：座標ごとの値、未指定セルの既定値、参照する会場・配置。明るい／暗いなどの判断理由も説明として残す。
- 評価への作用を再現するための `Scale`、`Offset`、`OverallWeight`。既定値を勝手に補って元の意図を変えない。
- 知見自体のマル秘フラグ。通常イベントから取り出す知見にも、書出し時に明示的に付けられるようにする。

「入力ルールと説明だけのひな形」と「特定の会場・配置の重みマップ付き」の２通りを推奨する。前者は別会場でも参照でき、後者は対応する会場・配置の確認が必要。選択画面では両者を区別し、必要な会場・配置を同梱するか、取込先の既存配置へ明示的に対応付ける。

### 現行実装と拡張時の注意点

現行の `EvaluationFeature` には名前・説明・`SourceColumn`・補正係数があり、`WeightMap` はチャンネルID、既定値、座標別の重みを持つ。ただし保存先は `CircleSpaceProject.Evaluation` であり、重みマップはフレーム配置案ごとに独立していない。画面で配置を選んで重みを編集することと、配置ごとに重みを所有することを混同しない。

`ChannelEditor.Upsert` は実際に存在する参加者の列を要求する。`RefreshValues` は空欄を0にする一方、列欠落や数値でない値は拒否する。値を0/1だけに制限する専用ルールや、列仕様を独立保存するモデルは現行の型にはない。知見の取込みをこの編集処理へそのまま接続せず、実データなしで保存できる構造を設計する。

取込み時は、推奨列名を保持した「未対応付け」の状態を認め、利用者が自分のサークルデータを別途取り込んだ後に列を対応付ける案とする。同名列だけで意味が同じと判断せず、入力ルールを確認する。未対応のチャンネルを評価済みとして扱ったり、列欠落を黙って全員0として処理したりしない。

現行の重みはイベント共通なので、新しいマップの適用が他の配置案に与える影響も確認する。同ID・同名の既存チャンネルを上書きせず、追加・見送り・明示的な対応付けを設計する。異なる会場の同じ座標へ無条件に重みを貼り付けない。

### 内部共有とマル秘

サークル情報がなくても、会場の評価や配置方針は運営内部の知見になり得る。配布前に説明・列仕様・重みマップを確認し、必要なら知見単体をマル秘にできるようにする。マル秘の警告・取込先への継承・再書出し時の保持を適用する。ひな形だけの保存でもフラグを保持する。

パッケージのマル秘は、元イベント・選択案・選択した知見・書出し時の指定の論理和とする案。部分取込みでもパッケージのマル秘を継承する。社内・運営内のファイル共有で利用できることを目指し、自動送信・公開やアクセス制御の実装をこの要件から自動的に追加しない。

## 画面の流れ

### エクスポート

［部分書出し］→対象一覧で選択→関連データの確認→名前・説明・タグの入力→書出し内容の確認→保存先選択→書出し。

初版の一覧はフレーム配置案の名前とチェック欄。会場・定義などの必須項目は同梱理由を表示する。未選択時は確定できない。最終確認には選択した案、同梱される内容、マル秘表示を示す。元イベント名や説明を無条件で転記せず、実際に書き出す内容を確認できるようにする。

### インポート

［部分読込み］→ファイル選択・形式検証→内容と説明を表示→取り込みたい項目を選択→名前・衝突・依存を確認→変更内容を確認→一括で適用。

初期状態では何も選択せず、［すべて選択］も用意する案とする。選択に応じて必要なデータを再計算し、未選択の案だけが使う型や設定は取り込まない。最初は項目名・件数・会場差分・追加予定名の一覧で確認できればよく、キャンバス上の重ね合わせ表示は後続とする。

取り込み後は追加件数と名前、通常のイベント保存で変更を残せることを表示する。

## 衝突・依存・履歴の推奨規則

- 初版は新しい案として追加する。同名は重複しない名前の入力または見送りで解決し、同名・同IDだけを根拠に既存案を更新しない。
- 複数案の取込みはひとつの操作とし、途中の１件が失敗した場合もイベント・履歴を部分更新しない。Undo/Redoも１回で全件を扱う。
- 元IDと取込先IDの対応表を作る。IDの有効範囲を調査し、型や配置への参照を一貫して張り替える。名前一致だけで同一データと判断しない。
- 会場はイベント内で共通。初版は現行の未配置判定・形状比較を継承し、既存配置がある場合の形状不一致は取込み不可とする。会場名の保持／採用も確認画面に示す。
- ブロック表示の衝突は初版では理由を表示して拒否する。更新・置換は後続段階で影響範囲を示す専用規則を設計する。
- 確認中に対象イベントが編集された場合は、古い確認結果を適用せず、再確認を求める。
- 共通カタログは暗黙に変更しない。定義のみの取込みを追加するときに、保存先を明示する。
- キャンセル、検証エラー、未対応形式ではイベントを変更しない。書出しは一時ファイルを完成させてから置換する既存方式を活用する。

## ファイル形式と知見の説明

新形式の名称案は `.project-portable.json`、`kind: circle-space-project-portable`、`formatVersion: 1`。現行 `.frame-layout.json` のversion 1の意味は変更しない。

新形式には一覧用の項目ID・種類・名前・依存関係、実データ、マル秘、任意の説明・タグを保持する案とする。パッケージID・作成日時は出所の識別用で、既存案への自動更新キーにはしない。項目一覧と実データの不一致は検証エラーにする。項目一覧の具体的なJSON構造は実装計画の第０段階で確定する。

知見として「用途」「配置の狙い」「適用条件」を説明に残せるようにする。初版はファイルの保存と説明の表示まで。フォルダー内検索、サムネイル、タグによるライブラリー画面は後続とする。

旧 `.frame-layout.json` は、新しい読込み画面でも１件の選択候補として扱えるようにする。通常のプロジェクトJSONを任意に切り取って取り込む機能は初版に含めない。旧アプリで新形式を開けることは保証しない。

## マル秘と含める範囲

現行のマル秘表示・書出し前と適用前の警告を継承する。初版はパッケージ全体のフラグを、元イベントまたは選択案のマル秘の論理和とする。選択した一部だけを取り込む場合も、パッケージがマル秘なら取込案と取込先イベントへ継承する保守的な規則とする。既存のマル秘を解除しない。マル秘は暗号化やアクセス制御ではない。

本計画ではサークル情報、入力元表、ローカルパス、操作ログ、画面状態、評価結果、アプリ設定を含めない。除外する項目を後から列挙するだけでなく、許可した項目からデータを組み立てる。チャンネルが参照する列名・意味・入力ルールは含められるが、参加者ID、サークル名、各行の入力値・計算済み属性値、割当・仮置きは含めない。2026-09-17の追加要望により、以前の案にあった「将来のサークル情報同梱」は本計画から外す。

## 後続実装で具体化する事項

1. 定義のみを取り込む先と、配置用定義／共通カタログへの登録導線。
2. 既存データの更新・置換・差分採用に必要な同一性判定と参照保護。
3. 部分配置の座標変換、切り出し境界、番号・接続の補正。
4. 重みチャンネルの入力ルールの保存、未対応付け状態、イベント共通マップの影響範囲と既存配置への対応付け。
5. ライブラリー画面の保存場所・検索・説明編集と、出所情報の保持範囲。

初版の選択式受け渡しを実装するために、上記すべての決定を待つ必要はない。詳細は実装時に現行コードと照合し、この文書と実装計画を更新する。
