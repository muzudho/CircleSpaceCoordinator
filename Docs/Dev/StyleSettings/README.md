# スタイル設定をほかの画面へ展開するための実装指針

2026-09-21 のイベント一覧への導入で得た知見です。現在の実装と、次の画面で採用を勧める改善を区別して記載します。文房具 UI 全体の仕様ではなく、このアプリへの接続方針です。

**原本は Git 管理し、配置計算と画面の動作を分離する。Debug は原本を監視し、Release はビルド時の設定を埋め込んで使う**、という構成を基本にしてください。

具体的な作業順序・確認項目・AI への依頼文は [横展開の手順](rollout-guide.md)、イベント一覧の調整項目は [利用ガイド](../../event-list-style-settings.md) を参照してください。

## 1. 原本と利用者の設定を分ける

| 対象 | このリポジトリーでの扱い |
| --- | --- |
| 画面の配置・寸法・余白 | `App_Doc/<page>.style-settings.md` に置いて Git 管理 |
| オートリロードの有効／無効 | ユーザーの `application-settings.json` の `styleAutoReload` に保存 |
| Debug の読み込み元 | ビルド時に AssemblyMetadata に記録した原本の絶対パス |
| Release の読み込み元 | C# アセンブリーの埋め込みリソース |

実装途中ではユーザー設定フォルダーへスタイルをコピーする方式を使いましたが、原本を Git でレビュー・共有する要件に合わせ、現在は `App_Doc` を直接読む方式に変更しています。別の画面を追加するときもユーザーフォルダーへの自動展開を復活させないでください。

拡張子は利用者の指定により `.style-settings.md` ですが、中身は **JSON** です。Markdown の見出し・説明文・コードフェンスは入れません。説明文は別の `.md` に書きます。これは文房具 UI の Markdown 対応を意味しません。エディターのファイル選択や整形機能がこの拡張子を扱えるかは別途確認が必要です。

## 2. 部品を作り直す前に、矩形だけを受け取る

イベント一覧では、文房具 UI の `StationeryStyleSettings` と `StationeryLayoutEngine` で矩形を計算し、既存の MonoGame 描画・`IconButtonModel` へ渡しています。`StationeryUiHost` への全面移行はしていません。

新しい対象画面でも、まず「ヘッダー」「本文」「一覧」「操作欄」などの安定した領域から移します。既存の入力・保存・遷移処理は維持し、必要に応じて領域の内部を次の段階で移行してください。

| JSON に置くもの | C# が受け持つもの |
| --- | --- |
| モデルの Id・型・親子関係 | データ取得、コントロール生成、イベント接続 |
| 行列の px / rate、セル割当 | 表示モードの選択、内容依存のサイズ計算 |
| 外周・領域内の余白、部品の配置先 | 色・フォント・文言、保存・遷移・モーダル制御 |
| 一覧行の配置ひな型 | 表示行数、スクロール、選択、繰り返し配置 |

JSON が計算する領域と、既存の C# が計算する領域を明示します。同じ部品へ両方の座標を適用したり、同じ余白を二重に引いたりしないようにします。

## 3. Id・型・パスをアプリとの契約にする

パーサーが JSON として受け付けても、アプリに必要なボタンが配置されるとは限りません。設定を採用する前に、画面固有の検証を行います。

- 必須モデルの完全パスと型が存在するか。
- 必須部品にセル割当があるか。未配置モデルは自動的に非表示になるとは限りません。
- C# が参照するレイアウトと、親モデルへの binding があるか。
- 行高など、C# が計算に使う値が有効か。0除算や無限値を避けられるか。
- 通常・小サイズ・0サイズで配置計算を実行できるか。

イベント一覧は `/events` 配下の固定パスを使います。別画面にはその画面固有のルートと役割を定義し、`/events` や `eventRow` をそのまま流用しないでください。寸法調整を目的とする段階では、モデル階層を自由に変更できる設計にしない方が接続を保ちやすくなります。

**改善案：** 操作名・モデルパス・コールバックを同じ定義にまとめると、追加や並べ替えで対応がずれる事故を減らせます。現在のイベント一覧には、`Actions` 配列と `Add(...)` 呼び出し順の対応が残っています。横展開時にこの順序依存を増やさないことを勧めます。

## 4. 描画と入力は同じ配置結果を使う

画面が動いてもクリック判定が古い場所に残ると、見た目だけ直って操作が壊れます。描画、クリック、ホバー、フォーカス枠、必要なら IME の表示位置まで、同じ座標変換と配置結果につなぎます。

イベント一覧では `EventListLayout` が返す矩形を描画と入力で共有しています。上部の作業者バー32pxを除いた高さで配置し、画面座標へ戻すときに Y 原点を一度だけ加えます。

別画面で倍率やスクロール原点を使う場合は、それらも配置の前提条件に含めます。文房具 UI のホストへ渡すときは、配置結果のピクセル座標とホストの論理座標の違いも確認してください。

## 5. リロードは「検証後に採用」の順にする

現在のイベント一覧は次の順序で更新します。

```text
Update で監視（約500ms間隔）
  → 同じ変更内容を2回読めたことを確認
  → JSON の解析
  → 画面固有の検証・配置計算の試行
  → Current を置き換え、Revision を増やす
  → 入力処理前に配置キャッシュを更新
```

書き込み途中・不正な JSON・必須部品の欠落では、正常な `Current` を維持し、画面へエラーを出します。初回読み込みに失敗した場合は埋め込み設定を使います。原本を自動修復したり、既定値で上書きしたりしません。

同じ内容を2回読めることは「保存完了」の厳密な保証ではありません。最後に解析と契約検証を通すことが必要です。また、埋め込み設定自体が不正なら起動時に失敗します。Release の埋め込み原本にも検証が必要です。

監視の設定はアプリケーション設定を唯一の保存元とします。現在は `StationeryStyleFile` 専用の別設定ファイルを作らず、`EventListStyle` が監視します。画面の切り替え操作は、設定ファイルへの保存成功後にメモリー上の設定を変更します。保存失敗を黙って無視して「無効になった」と表示しないようにします。

## 6. キャッシュ更新と作業状態の維持を別々に考える

ウィンドウ寸法が同じでも、スタイルが変われば再配置が必要です。現在のイベント一覧は幅・高さ・`Revision` をキャッシュの条件にしています。別画面では倍率・表示モード・内容依存の寸法なども必要に応じて追加してください。

リロード時にページ全体を生成し直さず、選択・スクロール・編集中の文字・キーボードフォーカスを維持します。一方、配置が動いたときの「押下中のボタン」は解除し、古い位置で押した操作が新しい位置の別ボタンへ届かないようにします。

現在のイベント一覧は配置更新時に操作ボタンを再生成しますが、選択とフォーカスは別フィールドに保持しています。入力欄がある画面ではこの方式をそのままコピーせず、入力モデルや IME の状態を維持して Bounds だけを更新する方が適しています。

## 7. 小さい画面と繰り返し行を明示的に扱う

イベント一覧には通常配置と2列のコンパクト配置があります。通常の操作欄に固定行の合計高さが収まるかで切り替えます。切り替え自体は C# の処理で、文房具 UI のメディアクエリー機能ではありません。

一覧行は JSON の `rowTemplate` を C# が繰り返し使います。最終行が領域をはみ出さないように表示行数を計算し、0行しか入らない場合も認めます。常に最低1行を描く設計は、小さい画面ではみ出す原因になります。

文房具 UI にない `auto` サイズや自動折り返しを実装済みと考えないでください。行・列間の間隔は空きトラックでも表せますが、クリッピングやスクロールは別途接続が必要です。

## 8. 共通化するなら読み込みの仕組みから

**次の画面を追加する際の改善案であり、現時点で共通サービスが実装済みという意味ではありません。**

ページ固有の検証や配置分岐まで汎用化するより、次の境界で分けると横展開しやすくなります。

| 共通化候補 | ページ固有のままにするもの |
| --- | --- |
| 埋め込みリソースの読み込み、Debug の原本選択 | リソース名と原本の指定 |
| 監視間隔、変更候補、無効→有効時の再確認 | 必須パス・型・binding の検証 |
| 正常な設定の保持、Revision、LastError | 領域取得、表示モード選択、繰り返し行 |
| アプリケーション設定からの監視方針 | ページの入力・保存・状態管理 |

読み込みクラスをページごとに丸ごと複製すると、監視再開やエラー復旧の修正がばらつきます。2つ目の画面で共通部分を抽出し、既存の監視テストも共通部分へ移すのがよいタイミングです。複数ページが同じ原本を使う場合は、同じファイルをページごとに監視せず設定スナップショットを共有する案も検討します。
